# 16 — Population growth (+1 NPC every 3 rounds)

**What to build:** On the night→day transition where the new round number is a multiple of 3, spawn 1 new NPC at the colony center or an existing House, with a role assigned, but only if the colony is under its population cap.

**Blocked by:** 15 — House & population cap, 12 — NPC Role System.

**Status:** done

- [x] New `population.py` (pygame-free): `maybe_spawn_npc(world, round_number, transitioned) -> NPC | None`
- [x] Spawns exactly on rounds 3, 6, 9, ... at the night→day transition, never mid-round or on other transitions — reuses the `transitioned` bool `game.py` already captures for the save-checkpoint hook (ticket 11), don't add a second polling mechanism
- [x] Suppressed once `len(world.npcs) >= population_cap(world)` (ticket 15's helper)
- [x] Spawned NPC has a valid role (reasonable default: round-robin or random across the 3 roles)
- [x] `game.py`'s `update()` calls this as one more additive consumer of `transitioned`, alongside the existing save-checkpoint call
- [x] Unit tests: spawns on round 3/6/9, suppressed at cap, spawned NPC has a role

**Implementation notes:** `round_number` alone is not enough to detect "night→day" - `day_night.py`'s `DayNightCycle.update()` only bumps `round_number` on the night→day half of a round, so the *same* `round_number` is observed on both the night→day transition into round N and the following day→night transition back out of round N. `maybe_spawn_npc(world, round_number, transitioned)` trusts its caller to have already resolved that ambiguity - `game.py` passes `transitioned and self.cycle.phase == DAY`, which is true only on the night→day half (phase has already flipped to `DAY` by the time `transitioned` is `True`). This keeps `population.py` itself simple and free of any day/night-phase concept, at the cost of the direction check now living in `game.py` rather than being self-contained in the new module; `test_population.py`'s `test_direction_gate_prevents_double_spawn_when_round_repeats_across_transitions` drives a real `DayNightCycle` through the exact composition `game.py` uses to cover that this doesn't double-spawn, since `game.py` itself isn't unit tested.

The `maybe_spawn_npc(...)` call sits *before* the existing `if transitioned: save_checkpoint(...)` block in `update()`, not after - a checkpoint written at the round-3 night→day transition needs to include the newly-spawned NPC, otherwise a quit-and-reload mid-day-3 would silently lose the spawn (the next `transitioned` event is the round-3 day→night transition, which the phase gate correctly blocks, and round 4 isn't a multiple of 3, so the NPC would never come back). Still a single added line, no restructuring of the existing `if transitioned:` block.

Role assignment reuses `world.py`'s round-robin-over-`ROLES` idea: `ROLES[len(world.npcs) % len(ROLES)]`, continuing the same sequence the starting 3-NPC colony used. It skews after NPC deaths (the role index is driven by current population count, not a persistent counter) - acceptable per the ticket ("either is fine, just be consistent"), noted here rather than treated as a bug.

**Persistence check:** confirmed no `save.py` changes were needed. A spawned NPC is constructed via the same `NPC(x, y, role=role)` path every other NPC uses. On load, `save.py` passes `role=nd.get("role")` into the `NPC` constructor, which re-derives `attack`/`defense`/`max_health`/`combat_range`/`work_multiplier` from `ROLE_STATS` exactly as it would for any fresh role-bearing NPC; the loader then explicitly overwrites `attack`/`defense` from the saved dict (redundant today since neither ever diverges from its role's static value post-spawn, but harmless) while `max_health`/`combat_range`/`work_multiplier` are left as the role-derived values and never round-tripped through the save file at all. None of this is new - it's the exact pre-existing behavior ticket 12 already established for every role-bearing NPC, and a population-growth spawn doesn't touch it. `tests/test_save.py`'s `_build_nontrivial_state()` fixture already exercises a role-bearing NPC, so no fixture changes were needed either.

Since `BASE_POPULATION_CAP` (3) equals `STARTING_NPC_COUNT` (3), a fresh colony starts already at cap - growth only materializes once at least one House has been built, raising `population_cap(world)`. `test_spawn_allowed_once_a_house_raises_the_cap` covers this realistic path explicitly rather than only testing spawn logic against an artificially empty `World(npc_count=0)`.

Found but out of scope: `game_over_state.check(...)` runs earlier in the same `update()` tick than the new `maybe_spawn_npc(...)` call. If all NPCs die on the exact tick a round-3 night→day transition also fires, the spawn call would still add an NPC into an already-game-over world. This is a pre-existing ordering quirk in `update()`'s control flow (not something this ticket's constraints allow restructuring - "one new line/call... don't restructure existing control flow") and is a one-tick cosmetic edge case, not a functional bug (the game-over screen is already showing); left as-is.

**`/code-review medium` fixes:**
1. Spawning unconditionally at `tile_center(width // 2, height // 2)` ignored the case where a Wall had been built exactly on that tile - buildings allow free placement on any claimed empty tile with no adjacency rule, so this is reachable, not hypothetical. A center-spawned NPC standing on a Wall tile would be permanently unable to path to any task: `task.py`'s `_try_claim_and_path` treats a Wall-occupied tile as impassable even for the NPC standing on it (`find_path`'s `is_walkable` rejects the NPC's own start tile), so it would silently occupy a population slot forever with no way to work. `build_task.py` already has a comparable displacement fix (`_displace_npcs_from_wall`) for NPCs standing on a tile a Wall is *newly built onto*, but that only fires at build time - it doesn't help a spawn placed there afterward. Fixed by adding `population.py`'s own `_spawn_tile(world)`: tries the center tile first, falls back to the nearest claimed, non-Wall-blocked neighbor, using the same 4-cardinal-then-diagonal delta order as `_displace_npcs_from_wall` - but a deliberately simpler single pass, not a call-through. `_displace_npcs_from_wall` runs a claimed-preferred pass and then a second any-unblocked-regardless-of-claimed fallback pass, because a Wall built at the map edge could have no claimed neighbor at all; `_spawn_tile` only ever searches around the colony center, where `START_CLAIM_RADIUS=5` guarantees every neighbor is already claimed, so the second pass would be dead code here and was left out. Covered by `test_spawn_avoids_a_wall_built_on_the_colony_center_tile`.
